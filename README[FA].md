## ۱. معرفی

**Ultimate Proxy Tester (UPT)** یک ابزار خط فرمان پایتون برای آزمایش پروکسی‌هایی است که خودت به برنامه می‌دهی. این ابزار ابتدا ارتباط اولیه یا **Handshake** را بررسی می‌کند و اگر مرحلهٔ دوم را فعال کرده باشی، با یک درخواست خارجی اتصال را **تأیید (Verification)** می‌کند. نتیجه‌ها هنگام اجرا در فایل‌های متنی و JSON ذخیره می‌شوند.

این ابزار **پروکسی پیدا یا تولید نمی‌کند**؛ برای بررسی فهرستی از آدرس‌های موجود است. موفقیت در یک آزمایش هم تضمین نمی‌کند که آن پروکسی برای تمام سایت‌ها و سرویس‌ها کار کند.

## ۲. قابلیت‌ها

| قابلیت | عملکرد موجود در کد |
| :--- | :--- |
| حالت HTTP | اجرای Handshake پروکسی HTTP و در صورت نیاز بررسی اتصال به مقصد HTTPS با `aiohttp` |
| حالت SOCKS | آزمایش Handshakeهای SOCKS5 و SOCKS4 |
| بررسی دومرحله‌ای | Handshake و سپس Verification اختیاری |
| اجرای هم‌زمان | تعیین Workerهای هر مرحله و سقف اتصال‌ها |
| مشخصات ورود | پذیرش نام کاربری و رمز عبور در قالب‌های پشتیبانی‌شده |
| آدرس‌ها | پشتیبانی از IPv4، نام دامنه و قالب‌های قابل پذیرش IPv6 |
| اطلاعات مکانی | کشور و شهر با `geoip2` و فایل پایگاه دادهٔ اختیاری |
| گزارش‌ها | نوشتن تدریجی نتیجه‌ها در TXT و JSON |
| رابط اجرا | ورودی تعاملی و نمایش جزئیات در حالت `--verbose` |

**نکتهٔ فنی:** وجود `https://` یا `socks5://` در ابتدای آدرس لزوماً حالت بررسی را تعیین نمی‌کند. حالت آزمایش باید جداگانه انتخاب شود. کد فعلی برای اتصال اولیه به پروکسی HTTPS، TLS برقرار نمی‌کند؛ بنابراین پشتیبانی از پیشوند `https://` در ورودی را نباید به معنی پشتیبانی تأییدشده از «پروکسی HTTPS رمزگذاری‌شده» دانست.

## ۳. پیش‌نیازها و نصب

- **Python 3.10 یا بالاتر توصیه می‌شود.** اجرای واقعی به سیستم‌عامل و نسخهٔ پایتون هم بستگی دارد.
- دسترسی شبکه به آدرس‌های مورد آزمایش و سرویس بررسی خارجی.
- کتابخانهٔ `aiohttp` برای مرحلهٔ تأیید HTTP.
- در صورت نیاز به GeoIP: کتابخانهٔ `geoip2` و فایل پایگاه دادهٔ سازگار.

پوشهٔ پروژه را از GitHub دانلود و استخراج کن یا آن را با Git Clone بگیر. سپس در پوشهٔ پروژه ترمینال باز کن.

**ویندوز (PowerShell یا CMD):**

```powershell
py -m pip install -r requirements.txt
py UPT.py
```

**لینوکس، مک یا Termux:**

```bash
python3 -m pip install -r requirements.txt
python3 UPT.py
```

در Termux اگر Python نصب نیست، با دستور `pkg install python` نصبش کن. در سیستم‌هایی که فرمان پایتون `python` است، همان نام را جایگزین کن.

## ۴. اجرای تعاملی

برای واردکردن تنظیمات و پروکسی‌ها در خود برنامه:

```bash
python UPT.py
```

مراحل کار:

۱. حالت بررسی **HTTP / HTTPS** یا **SOCKS4 / SOCKS5** را انتخاب کن.  
۲. فهرست آدرس‌ها را دستی وارد کن یا از فایل بخوان.  
۳. در حالت ورود دستی، پس از واردکردن آدرس‌ها، **سه بار پشت‌سرهم در خط خالی Enter بزن**.  
۴. Timeout، تعداد Workerهای Handshake و Verification، فعال‌بودن بررسی دوم، حالت نمایش جزئیات و سقف اتصال‌ها را تنظیم کن.  
۵. منتظر پایان بررسی بمان؛ نتیجه‌های تکمیل‌شده هنگام کار نوشته می‌شوند.

**توجه:** بالا بردن بیش‌ازحد تعداد اتصال‌ها ممکن است خطا و فشار روی دستگاه یا شبکه را بیشتر کند؛ عدد بالاتر لزوماً نتیجهٔ بهتری نمی‌دهد.

## ۵. اجرا با دستورهای ترمینال

**خواندن آدرس‌ها از فایل:**

```bash
python UPT.py --type http --file proxies.txt
```

**آزمایش SOCKS و نمایش نتیجهٔ هر پروکسی:**

```bash
python UPT.py --type socks --file proxies.txt --verbose
```

**فقط Handshake، بدون مرحلهٔ تأیید دوم:**

```bash
python UPT.py --type http --file proxies.txt --no-verify
```

**تنظیم منابع و زمان انتظار:**

```bash
python UPT.py --type socks --file proxies.txt --connect-timeout 3 --read-timeout 5 --handshake-workers 50 --verify-workers 20 --max-conn 100
```

**نمایش همهٔ گزینه‌ها:**

```bash
python UPT.py --help
```

### گزینه‌های برنامه

| گزینه | مقدار پیش‌فرض | کاربرد |
| :--- | :--- | :--- |
| `--type` | `http` | انتخاب حالت `http` یا `socks` |
| `--file` | ندارد | خواندن آدرس‌ها از فایل |
| `--proxies` | ندارد | دریافت آدرس‌های جداشده با ویرگول از خط فرمان |
| `--connect-timeout` | `2.0` | مهلت اتصال، به ثانیه |
| `--read-timeout` | `3.0` | مهلت دریافت پاسخ Handshake |
| `--handshake-workers` | `100` | تعداد Workerهای مرحلهٔ اول |
| `--verify-workers` | `30` | تعداد Workerهای مرحلهٔ دوم |
| `--no-verify` | غیرفعال | حذف مرحلهٔ دوم |
| `--verbose` | غیرفعال | نمایش جزئیات هر نتیجه |
| `--max-conn` | `500` | سقف عملیات هم‌زمان در مراحل بررسی |

مقادیر Timeout و تعداد Workerها باید مثبت باشند. مرحلهٔ Verification مهلت‌های داخلی مجزایی هم دارد؛ بنابراین `--read-timeout` همهٔ Timeoutهای برنامه را تغییر نمی‌دهد.

**هشدار:** استفاده از `--proxies` با مشخصات ورود، ممکن است رمز عبور را در تاریخچهٔ ترمینال یا فهرست پردازش‌ها آشکار کند. برای فهرست‌های حساس بهتر است از یک فایل محلی محافظت‌شده استفاده کنی.

## ۶. فرمت‌های ورودی

```text
host:port
user:pass@host:port
http://host:port
http://user:pass@host:port
socks5://host:port
host:port:user:pass
[2001:db8::1]:1080
```

آدرس‌های نمونهٔ زیر مخصوص مستندات هستند و **پروکسی فعال محسوب نمی‌شوند**:

```text
192.0.2.10:8080
http://198.51.100.20:3128
socks5://203.0.113.10:1080
```

- حالت HTTP یا SOCKS را خودت انتخاب کن؛ `--type` تشخیص خودکار پروتکل نیست.
- بهتر است آدرس‌های HTTP و SOCKS را در دسته‌های جداگانه آزمایش کنی.
- نام دامنه و IPv6 داخل کروشه در قالب‌های قابل پذیرش پشتیبانی می‌شوند، مشروط به دسترسی شبکه.
- آدرس‌ها را در خط‌های جداگانه یا با ویرگول وارد کن. تکراری‌ها بر اساس پروتکل، میزبان، پورت و مشخصات ورود حذف می‌شوند.
- اطلاعات ورود واقعی را در ریپازیتوری عمومی قرار نده.

## ۷. مراحل آزمایش

```text
فهرست ورودی
     |
     v
تجزیه و حذف تکراری‌ها
     |
     v
مرحلهٔ اول: Handshake
     |
     +---- ناموفق --> در فهرست موفق‌ها ثبت نمی‌شود
     |
     v
مرحلهٔ دوم: Verification (اختیاری)
     |
     v
result.txt و result.json
```

**Handshake:** برنامه به آدرس پروکسی متصل می‌شود و درخواست آغازین پروتکل را ارسال می‌کند. این مرحله به‌تنهایی ثابت نمی‌کند که پروکسی می‌تواند درخواست‌های واقعی را عبور دهد.

**Verification:** در مرحلهٔ دوم، درخواست بررسی به یک سرویس خارجی ارسال می‌شود. در حالت HTTP مقصدهای HTTPS از طریق `aiohttp` استفاده می‌شوند، ولی بررسی SOCKS با درخواست HTTP معمولی انجام می‌شود. بعضی سرویس‌های مقصد ممکن است مسدود یا موقتاً در دسترس نباشند.

بنابراین شکست در مرحلهٔ دوم الزاماً به معنای خراب‌بودن پروکسی برای تمام مقصدها نیست و موفقیت آن هم ضمانت کارکرد روی تمام سایت‌ها محسوب نمی‌شود.

**Latency:** زمان نشان‌داده‌شده مربوط به عملیات آزمایش است، نه سرعت دانلود، پهنای باند یا کیفیت کلی شبکه.

## ۸. خروجی‌ها و وضعیت‌ها

نتیجه‌ها در **پوشه‌ای ذخیره می‌شوند که دستور را از آن اجرا می‌کنی**:

| فایل | محتوا |
| :--- | :--- |
| `result.txt` | نتیجه‌های متنی شامل نوع، آدرس، تأخیر و وضعیت |
| `result.json` | داده‌های ساختاریافته شامل نوع، میزبان، پورت، زمان‌ها، وضعیت و موقعیت اختیاری |

معانی وضعیت‌ها:

- **`OK`**: مرحلهٔ مربوطه موفق بوده؛ با توجه به فعال‌بودن Verification معنایش فرق دارد.
- **`FAILED`**: Handshake موفق بوده اما تأیید مرحلهٔ دوم موفق نشده است.
- **`AUTH`**: پاسخ مربوط به نیاز یا خطای احراز هویت، در موارد قابل تشخیص.

برخی آدرس‌هایی که در **Handshake اولیه شکست می‌خورند** اصلاً در فایل نتیجه ثبت نمی‌شوند. بنابراین تعداد نتیجه‌ها ممکن است از تعداد ورودی‌ها کمتر باشد. هر اجرای جدید ممکن است فایل‌های `result.txt` و `result.json` قبلی را بازنویسی کند؛ در صورت نیاز قبلاً از آن‌ها کپی بگیر.

## ۹. موقعیت جغرافیایی اختیاری

نصب وابستگی:

```bash
python -m pip install -r requirements-geoip.txt
```

فایل سازگار پایگاه دادهٔ City را با نام `GeoLite2-City.mmdb` کنار `UPT.py` قرار بده. در حالت تعاملی، اگر `geoip2` نصب باشد و پایگاه داده پیدا نشود، برنامه می‌تواند دانلود آن را از یک منبع شخص ثالث در GitHub پیشنهاد کند.

- مکان GeoIP **تقریبی** است، نه موقعیت قطعی فیزیکی سرور.
- فایل پایگاه داده داخل بستهٔ پروژه قرار ندارد.
- قبل از دریافت یا بازنشر پایگاه داده، دربارهٔ منبع و مجوز استفاده از آن بررسی کن.

## ۱۰. رفع اشکال

| مشکل | راهکار |
| :--- | :--- |
| `ModuleNotFoundError: aiohttp` | وابستگی‌ها را با همان نسخهٔ Python که برنامه اجرا می‌کند نصب کن. |
| خطای نیاز به `aiohttp` در تأیید HTTP | `aiohttp` را نصب کن یا با `--no-verify` فقط Handshake را آزمایش کن. |
| `No valid proxies extracted` | فرمت آدرس، پورت و مسیر فایل ورودی را بررسی کن. |
| همهٔ آدرس‌ها ناموفق‌اند | نوع پروتکل، اطلاعات ورود، Timeout، اتصال شبکه و دسترسی مقصدهای آزمایش را بررسی کن. |
| موقعیت جغرافیایی نشان داده نمی‌شود | `geoip2` و فایل MMDB سازگار را بررسی کن. |
| فایل نتیجه خالی است | شکست‌های مرحلهٔ اول به‌صورت نتیجهٔ موفق ثبت نمی‌شوند؛ خروجی ترمینال را هم بررسی کن. |
| فایل خروجی پیدا نمی‌شود | پوشهٔ جاری ترمینال و مجوز نوشتن فایل را بررسی کن. |

## ۱۱. امنیت و محدودیت‌ها

- **مجوز:** فقط پروکسی‌هایی را بررسی کن که مالک آن‌ها هستی یا اجازهٔ آزمایششان را داری.
- **محرمانگی:** فهرست پروکسی‌ها، تاریخچهٔ خط فرمان و فایل‌های نتیجه ممکن است آدرس‌ها یا اطلاعات حساس را فاش کنند.
- **انتقال داده:** بعضی مراحل از HTTP بدون رمزگذاری استفاده می‌کنند. این ابزار «بررسی‌کنندهٔ کاملاً رمزگذاری‌شدهٔ سرتاسری» نیست.
- **سرویس‌های خارجی:** سرویس بررسی IP درخواست‌ها را دریافت می‌کند و ممکن است ترافیک خروجی پروکسی را مشاهده کند.
- **مصرف منابع:** تعداد بسیار زیاد Workerها می‌تواند به شبکه، سیستم و سرویس‌های مقصد فشار بیاورد.
- **محدودیت نتیجه:** نتیجهٔ موفق به معنای ناشناس‌ماندن، امنیت کامل یا دسترسی بدون محدودیت نیست.
- **محدودهٔ آزمایش:** کد از نظر Syntax و دستور `--help` بررسی شده، اما در آماده‌سازی این بسته **آزمایش واقعی روی پروکسی‌ها انجام نشده** است.
